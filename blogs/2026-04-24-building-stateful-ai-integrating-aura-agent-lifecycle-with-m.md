<div><img alt="" class="attachment-large size-large wp-post-image" height="358" src="https://dist.neo4j.com/wp-content/uploads/20260429113617/1_SIlEBcf12oJTiLl7O2mLTA-1024x572.webp" style="margin-bottom: 15px;" width="640" /></div><h2>An exploration into creating a closed-loop system where agents don&rsquo;t just execute tasks, but learn and evolve through a dedicated memory&nbsp;layer.</h2><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*SIlEBcf12oJTiLl7O2mLTA.png" /><figcaption>Agent lifecycle as imagined by&nbsp;Gemini</figcaption></figure><p>Over the last two weeks since I got back from vacation, I&rsquo;ve seen a huge focus on agentic memory. It&rsquo;s all about <strong>agents learning</strong> about the user and their preferences, while also using past iterations to actually get better at solving&nbsp;tasks.</p><p>Building on that, we need a closed loop where the agent can learn and self-improve automatically, without any copy-pasting between systems. This is where we can put our approach to the test. Since Neo4j Aura Agents can be managed and invoked via an API, our main agent can build subagents on Neo4j Aura, evaluate them, and store what it learns in memory for persistence.</p><p><em>Disclaimer: I currently work at Neo4j, which is why I&rsquo;m using Neo4j as an&nbsp;example</em></p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*bBzhvcQJKwaAuf0xdxBvzg.png" /><figcaption>The idea behind building a self-learning agent than can improve and optimize the subagents it has available.</figcaption></figure><p>The diagram above illustrates this self-learning loop in&nbsp;action.</p><p>The main agent starts with goal determination and strategy, then moves through four key&nbsp;stages:</p><ol><li>building sub-agents tailored to the&nbsp;task,</li><li>invoking and executing them,</li><li>evaluating their performance, and&nbsp;finally</li><li>updating the sub-agents based on what worked and what&nbsp;didn&rsquo;t.</li></ol><p>Each iteration feeds back into the strategy, while all learnings and experiences are persisted to memory, allowing the agent to read from and write to a growing knowledge base over&nbsp;time.</p><blockquote>This closes the loop: the agent doesn&rsquo;t just solve a task once, it gets better at solving similar tasks in the&nbsp;future.</blockquote><p>With the architecture clear, the next decision is how to actually implement the memory layer. We need to choose how experiences and learnings are structured, stored, and retrieved, whether as raw traces, distilled lessons, or a graph of interconnected insights, and how the agent queries this memory when determining its strategy.</p><p>The right memory implementation is what turns a one-off execution pipeline into a system that genuinely compounds knowledge over&nbsp;time.</p><p>I like to keep it simple, and just recently, Andrej Karpathy <a href="https://x.com/karpathy/status/2039805659525644595" rel="noopener nofollow" target="_blank">introduced</a> his idea about <a href="https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f" rel="noopener nofollow" target="_blank">LLM Knowledge Bases.</a></p><h2>Andrej Karpathy on X (formerly Twitter): &#8220;LLM Knowledge BasesSomething I&#8217;m finding very useful recently: using LLMs to build personal knowledge bases for various topics of research interest. In this way, a large fraction of my recent token throughput is going less into manipulating code, and more into manipulating&#8230; / X&#8221;</h2><p>LLM Knowledge BasesSomething I&#8217;m finding very useful recently: using LLMs to build personal knowledge bases for various topics of research interest. In this way, a large fraction of my recent token throughput is going less into manipulating code, and more into manipulating&#8230;</p><p>Karpathy&rsquo;s idea is to instruct an LLM to build Wiki-style knowledge base using a repository of markdown files as storage. Instead of storing and indexing raw documents, the LLM processes documents and stores only interesting information to its Wiki. We can reuse this approach for storing agentic memory as well, the only distinction is to store learnings instead of information from documents.</p><p>Additionally, while markdown files are a natural abstraction for an LLM to work with, managing them directly in production can get messy fast. Beyond that, giving an LLM access to the terminal and file system is a real security concern. I recall seeing that LangChain recommends storing markdown content in a database while still presenting it as files to the LLM, which is a clean separation of concerns. We&rsquo;ll take a similar approach here, using Neo4j to store the agentic memory, inspired by Karpathy&rsquo;s take on Knowledge Bases.</p><p>Throughout this blog post, we&rsquo;ll build an MCP server that will enable us to inspect databases, manage agents, and store learnings in&nbsp;memory.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*ExL_Nb9j7IFbZzUqMngL8g.png" /><figcaption>List of tool in Aura Agents Management MCP&nbsp;server.</figcaption></figure><p>The <strong>Database tools</strong> let us fetch the schema so the agent knows what data it&rsquo;s working&nbsp;with.</p><p>The <strong>Agents tools</strong> cover the full CRUD lifecycle plus invocation, so we can create, update, delete, and actually run sub-agents programmatically.</p><p>The <strong>Memory/Wiki group</strong> is the largest, since we don&rsquo;t have terminal commands to fall back on, we need dedicated tools for writing, reading, appending, searching, and linking memory&nbsp;pages.</p><p>The MCP is available on&nbsp;<a href="https://github.com/tomasonjo/aura-agents-management-mcp" rel="noopener nofollow" target="_blank">GitHub</a>.</p><p><a href="https://github.com/tomasonjo/aura-agents-management-mcp" rel="noopener nofollow" target="_blank">GitHub &#8211; tomasonjo/aura-agents-management-mcp: MCP server for the Neo4j Aura Agents API, plus a Karpathy-style LLM-authored wiki memory backed by Neo4j</a></p><p>Let&rsquo;s start by preparing the environment.</p><h3>Neo4j Aura and Aura&nbsp;Agents</h3><p>The idea is simple: if the agent can do tasks, learn about them, and update its approach, whether for knowledge graph creation or retrieval, it naturally becomes a self-improving loop. In this post, we&rsquo;ll implement that loop by allowing the agent to create and update <a href="https://neo4j.com/developer/genai-ecosystem/aura-agent/">Aura&nbsp;Agents</a>.</p><p>To follow along, you&rsquo;ll need a Neo4j Aura instance with data already loaded. If you don&rsquo;t have one yet, create an instance now. Be sure to select <strong>Graph Analytics</strong> as the plugin so the agents can access&nbsp;it.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*DjLU7Z51Ap1_YdKoRNdJqQ.png" /></figure><p>If your database is already populated, great. Otherwise, you can restore the <a href="https://drive.google.com/file/d/1gjFDgRN1zFHLnrfM4CJ7zVpLJ4cZvDc-/view?usp=sharing" rel="noopener nofollow" target="_blank">companies dump</a> I&rsquo;m using or load one of the <a href="http://console.neo4j.io/guides/sample-datasets" rel="noopener nofollow" target="_blank">sample datasets</a>.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*9kpgyjxlxBF9E94IcR3csA.png" /><figcaption>Some datasets available in Neo4j&nbsp;Aura.</figcaption></figure><p>Once your instance is up and populated, head to your organization&rsquo;s Settings and make sure <strong>Aura Agent</strong> is enabled under Preferences.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*vDbRgSZr1cjBaeiz_aENJg.png" /><figcaption>Enable Aura Agents under organization&rsquo;s settings.</figcaption></figure><p>Finally, you&rsquo;ll need <strong>Aura API credentials</strong> to interact with agents programmatically. Go to Account Settings, open the API keys tab, and generate a new key. Keep these credentials handy, we&rsquo;ll use them throughout the MCP server implementation.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*UHsHqwauA1ZgltCcl3lR8A.png" /></figure><p>Next, we&rsquo;ll implement the MCP&nbsp;server.</p><h3>Aura Agent Management MCP&nbsp;server</h3><p>The implementation of the MCP server is fairly straightforward. We have two types of tools, one that deals with agent lifecycle and execution, and the other, which allows the agent to store its learnings into persistent memory.</p><p><strong>Aura Agent lifecycle tools</strong></p><p>First, we&rsquo;ll implement Aura Agents lifecycle tools using the <a href="https://neo4j.com/docs/aura/platform/api/specification/?urls.primaryName=Aura%20v2beta1#/">Aura Agents API specification</a>. The available endpoints for agentic interface are:</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/952/1*l6uESJHLEq1KLuhPI79evQ.png" /></figure><p>Here, we can simply map endpoints to agentic tools one-to-one, requiring no transformation.</p><p>Additionally, we&rsquo;ll need tools to list existing databases and inspect their schema. For database lookup, we simplified the flow: instead of separate tools for listing orgs, projects, instances, and finally databases, a single tool iterates over all orgs, projects, and instances and displays every available database.</p><p>For schema lookup, we had to create a custom agent equipped with predefined schema tools, since the API doesn&rsquo;t expose direct Cypher access. The only way to query the database is by invoking an agent. Below is the definition of the schema agent with custom tools I implemented to be able to fetch&nbsp;schema:</p><pre class="code CodeMirror cm-s-paraiso-dark">agent = await _request(<br />    "POST",<br />    base,<br />    json={<br />        "name": "_schema_probe",<br />        "description": "Temporary agent for schema retrieval",<br />        "dbid": dbid,<br />        "is_private": False,<br />        "system_prompt": system_prompt,<br />        "tools": [<br />            {<br />                "type": "cypherTemplate",<br />                "name": "get_schema",<br />                "description": "Fetch the node/relationship schema via apoc.meta.schema().",<br />                "enabled": True,<br />                "config": {<br />                    "template": "CALL apoc.meta.schema() YIELD value RETURN value",<br />                    "parameters": [],<br />                },<br />            },<br />            {<br />                "type": "cypherTemplate",<br />                "name": "get_indexes",<br />                "description": "Fetch fulltext and vector indexes.",<br />                "enabled": True,<br />                "config": {<br />                    "template": (<br />                        "SHOW INDEXES YIELD name, type, labelsOrTypes, properties, options "<br />                        "WHERE type IN ['FULLTEXT', 'VECTOR'] "<br />                        "RETURN name, type, labelsOrTypes, properties, options"<br />                    ),<br />                    "parameters": [],<br />                },<br />            },<br />        ],<br />    },<br />)</pre><p>The agent is spun up on demand, queried for the schema, and torn down once the information has been retrieved. This effectively uses the agent layer as a thin proxy for the Cypher access we&rsquo;d otherwise call directly, keeping schema introspection self-contained and avoiding long-lived probe agents attached to the database.</p><p>On my example database you would get an answer like the following when inspecting a schema of the&nbsp;graph.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*LQDHwYI8MYE7iuS2HwRq0g.png" /><figcaption>Database schema information.</figcaption></figure><p><strong>Karpathy&rsquo;s memory&nbsp;module</strong></p><p>The second piece is the memory module. Without memory, the agent starts every session from scratch, losing any context or insights it built up previously. The memory module fixes this by giving the agent a place to write down what&rsquo;s worth remembering, so useful information carries across sessions.</p><p>In our MCP server, memory is optional. The agent runs fine without it, but if you supply credentials for a memory database, the module is wired in automatically.</p><p><em>This means you&rsquo;ll need a second Neo4j database to store the memory, separate from your main one. I&rsquo;m running a local instance for this, but anything works: a second Neo4j Aura instance, a Docker container, or any other Neo4j deployment you have&nbsp;handy.</em></p><p>Following Karpathy&rsquo;s idea, we expose memory through a familiar abstraction: a <strong>filesystem of markdown files</strong>. That&rsquo;s what the agent sees and interacts with. Behind the scenes, everything lives in Neo4j, structured with the graph model shown&nbsp;below.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*dlfAyrsUO_lJrugV8HkupQ.png" /></figure><p>The model is deliberately minimal. There&rsquo;s a single node type, Page, which represents one markdown file. Each page carries its path (the filesystem-style identifier the agent uses to read and write it), its content (the markdown body itself), and some bookkeeping fields: created_at, updated_at, size, a deleted flag for soft deletes, and a wiki field for grouping pages into separate namespaces.</p><p>The only relationship is LINKS_TO, a self-reference from Page to Page. Whenever one markdown file references another (think wiki-style [[links]]), we materialize that as an edge in the graph. This is what turns a flat pile of notes into something the agent can traverse, letting it follow connections between memories rather than just reading them in isolation.</p><p>Because the memory is just a filesystem, the agent is free to name pages however it wants, and left to its own devices it will. One session writes notes_about_db.md, the next writes db-info.md, the third buries the same facts inside log.md. The pages exist, but the agent can&#8217;t find them again, which defeats the point of having memory at&nbsp;all.</p><p>A small amount of guidance fixes this. By suggesting a layout in the system prompt, we nudge the agent toward consistent paths and a consistent sense of <em>what belongs&nbsp;where</em>.</p><pre class="code CodeMirror cm-s-paraiso-dark">Recommended page layout &mdash; organise memories by topic, not by<br />conversation, so they can be recalled independently of when they<br />were learned. Group facts and learnings about each *database* and<br />each *agent* under their own page so they can be retrieved<br />individually rather than scanning a single mixed log:<br /><br />    user/profile.md          # who they are, role, responsibilities<br />    user/preferences.md      # tooling, style, do / don't<br /><br />    databases/&lt;dbid&gt;.md      # one page per Aura database. Capture:<br />                             #   - purpose / dataset description<br />                             #   - schema quirks, label &amp; rel naming<br />                             #   - known-good Cypher patterns<br />                             #   - gotchas, slow queries, indexes<br />                             #   - links to related agents/concepts<br />    databases/&lt;dbid&gt;/&lt;topic&gt;.md  # optional sub-pages for deep dives<br />                             #   (e.g. databases/abc123/schema.md)<br /><br />    agents/&lt;agent_id&gt;.md     # one page per agent. Capture:<br />                             #   - what it's for, who uses it<br />                             #   - tool list and why each was chosen<br />                             #   - prompt-engineering lessons<br />                             #   - failure modes, fixes, retries<br />                             #   - link to its `databases/&lt;dbid&gt;.md`<br />    agents/&lt;agent_id&gt;/&lt;topic&gt;.md # optional sub-pages<br /><br />    entities/&lt;name&gt;.md       # people, orgs, services, repos<br />    concepts/&lt;name&gt;.md       # domain ideas worth knowing<br />    learnings/&lt;topic&gt;.md     # cross-cutting lessons not tied to one<br />                             # database or agent<br />    log.md                   # scratch / chronological notes</pre><p>The actual implemented tools for memory&nbsp;are:</p><ul><li><strong>write_memory</strong>&#8202;&mdash;&#8202;Save or overwrite a memory in your agentic&nbsp;memory.</li><li><strong>read_memory</strong>&#8202;&mdash;&#8202;Read a stored memory&nbsp;page</li><li><strong>append_memory</strong>&#8202;&mdash;&#8202;Append to an existing memory without rewriting it</li><li><strong>rename_memory</strong>&#8202;&mdash;&#8202;Atomically rename a memory; also rewrites [[old_path]] references</li><li><strong>delete_memory</strong>&#8202;&mdash;&#8202;Soft delete a&nbsp;memory</li><li><strong>list_memories</strong>&#8202;&mdash;&#8202;List memory pages with pagination, sorting, and&nbsp;metadata</li><li><strong>search_memory</strong>&#8202;&mdash;&#8202;Full-text search across your agentic&nbsp;memory</li><li><strong>find_memory_backlinks</strong>&#8202;&mdash;&#8202;Return all memories that link to a given&nbsp;one</li></ul><p>Probably, we could make the memory tools more flexible, so we wouldn&rsquo;t require eight of them. Otherwise we&rsquo;re ready to test it&nbsp;out.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*SlXoNhPTi82VPSdJipT6WA.png" /><figcaption>Example of memory&nbsp;usage.</figcaption></figure><p><strong>Running the MCP&nbsp;server</strong></p><p>You can run the MCP server in any MCP client. I use Claude Desktop, but it doesn&rsquo;t matter which one. To save yourself from cloning the repo, you can pull the MCP directly from GitHub using the snippet below. Just set up the environment and plug in valid credentials before running&nbsp;it.</p><pre class="code CodeMirror cm-s-paraiso-dark">{<br />  "mcpServers": {<br />    "aura_agents": {<br />      "command": "uvx",<br />      "args": [<br />        "--from",<br />        "git+https://github.com/tomasonjo/aura-agents-management-mcp",<br />        "aura-agents-management-mcp"<br />      ],<br />      "env": {<br />        "AURA_CLIENT_ID": "",<br />        "AURA_CLIENT_SECRET": "",<br />        "NEO4J_MEMORY_URI": "bolt://localhost:7687",<br />        "NEO4J_MEMORY_USERNAME": "neo4j",<br />        "NEO4J_MEMORY_PASSWORD": "password"<br />      }<br />    }<br />  }<br />}</pre><h3>Agentic self-learning loop</h3><p>Let&rsquo;s test how the agent learns, memorizes, and applies solutions to specific tasks. Our test case: building an agentic interface that efficiently retrieves information from Neo4j for a market intelligence scenario.</p><p><strong>Before we begin, two important notes:</strong></p><ol><li><strong>Token consumption:</strong> This process uses significant LLM tokens. Consider it an investment in cutting-edge experimentation (and yes, bragging rights for burning&nbsp;tokens).</li><li><strong>Aura Agents costs:</strong> This requires paying to run Aura&nbsp;Agents</li></ol><p>Let&rsquo;s begin by defining the task at&nbsp;hand.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*Jb5kCw7fz81-5w9RvFUY1Q.png" /></figure><p>We have one database available containing the <a href="https://drive.google.com/file/d/1gjFDgRN1zFHLnrfM4CJ7zVpLJ4cZvDc-/view" rel="noopener nofollow" target="_blank">companies dataset</a> with market intelligence information. The agent has proposed ideas for building Aura subagents, so let&rsquo;s get&nbsp;started.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*DT9v9qx0QBuKv2JndMkhJQ.png" /></figure><p>This is the part we are burning tokens &#128293;&#128293;&#128293;. The agent is creating Aura subagents, testing them, updating them, and learning about the process as&nbsp;well.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*EGwlhwu1fzD8a_AR8oteZQ.png" /></figure><p>So basically the agent has been running into walls and writing down what it learned each time. Pretty simple concept but it adds up&nbsp;fast.</p><ul><li>&#127961;&#65039; <strong>The city thing</strong>&#8202;&mdash;&#8202;turns out orgs have offices everywhere, so if you just grab the first city you find, you&rsquo;ll get garbage results. Collect them all first, then&nbsp;pick.</li><li>&#128269; <strong>The Tesla problem</strong>&#8202;&mdash;&#8202;searching by name sounds fine until you realize there&rsquo;s probably a &ldquo;Tesla Consulting LLC&rdquo; with one article that tanks your whole trend&nbsp;analysis</li><li>&#128197; <strong>Dates are annoying</strong>&#8202;&mdash;&#8202;some fields are strings, some are datetimes, they filter differently. Easy to miss, annoying when you&nbsp;do.</li></ul><p>The persisted part just means next time the agent spins up, it already knows all this. It doesn&rsquo;t have to relearn that ampersands break things or that Tesla is a common&nbsp;name.</p><p>In our memory graph, information is structured as pages, which contain markdown content and file paths. Pages can also reference one&nbsp;another.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/558/1*oaat9iVdLKGuY6wSAtHezg.png" /><figcaption>Agentic memory abstracting markdown files as Page&nbsp;nodes.</figcaption></figure><p>The first subagent iterations are implemented and tested. Time to build the next&nbsp;one.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*Pjk5kJr5tiDYHZ-06km3KQ.png" /></figure><p>This screenshot doesn&rsquo;t show the full picture. <strong>Claude is actually making a large number of tool calls and burning through tokens, with output that extends well beyond what&rsquo;s&nbsp;visible.</strong></p><p>What&rsquo;s happening underneath is that the model is observing its own environment, noticing what works and what doesn&rsquo;t, and adjusting its approach as it goes. <strong>With every iteration you get a better agent, but you also get something equally valuable: the learnings that come from watching it fail, recover, and find a different path.</strong></p><p>There&rsquo;s something genuinely powerful about giving a language model the ability to observe and reshape the environment it&rsquo;s operating in. It stops being a thing that answers questions and starts being a thing that figures out problems. The mistakes are part of that. Each run surfaces assumptions you didn&rsquo;t know you were making, edges you hadn&rsquo;t considered, and constraints that only become visible when something actually tries to push against&nbsp;them.</p><p>That feedback loop, where the model acts, observes the result, and tries again, is where most of the real progress&nbsp;happens.</p><p>For example, you could present the learning of the agent to your Product manager, like what it thinks about building text2cypher agents. Here we are using a new chat, so the information has to come from&nbsp;memory.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*TzX_N1uAVmLPs7vAhi3BQg.png" /><figcaption>Learnings from&nbsp;memory</figcaption></figure><p>Another option is to present your coworkers with a built-in chat interface for the created&nbsp;agents.</p><figure><img alt="" src="https://cdn-images-1.medium.com/max/1024/1*IJtqGOeYPDWLo7x6grQg7A.png" /><figcaption>Aura Agent chat interface.</figcaption></figure><h3>Summary</h3><p>What started as a thought experiment about agentic memory turned into something more concrete: <strong>a working loop where an agent builds subagents, tests them, fails at them, and writes down what it learned</strong> so the next attempt starts further ahead than the&nbsp;last.</p><p>The pieces themselves aren&rsquo;t&nbsp;exotic.</p><ul><li>An MCP server wrapping the Aura Agents API gives us lifecycle control.</li><li>A second Neo4j instance, modeled as Pages connected by LINKS_TO edges, gives us a Karpathy-style wiki the agent can read and write like a filesystem.</li><li>A small nudge in the system prompt about page layout keeps the memory from devolving into a pile of inconsistently named&nbsp;notes.</li></ul><p>None of it is heavy machinery, and that&rsquo;s kind of the&nbsp;point.</p><p>What makes this interesting isn&rsquo;t the infrastructure, it&rsquo;s what happens once all three pieces are wired together.</p><p>The agent stops treating each task as a fresh start. It remembers that organization names are messy, that date fields lie about their types, that certain Cypher patterns work better than others on a given&nbsp;schema.</p><blockquote>Those aren&rsquo;t insights we hardcoded, they&rsquo;re lessons the agent surfaced by running into walls and deciding the wall was worth writing&nbsp;down.</blockquote><p>The MCP is available on&nbsp;<a href="https://github.com/tomasonjo/aura-agents-management-mcp" rel="noopener nofollow" target="_blank">GitHub</a>.</p><p><a href="https://github.com/tomasonjo/aura-agents-management-mcp" rel="noopener nofollow" target="_blank">GitHub &#8211; tomasonjo/aura-agents-management-mcp: MCP server for the Neo4j Aura Agents API, plus a Karpathy-style LLM-authored wiki memory backed by Neo4j</a></p><img alt="" height="1" src="https://medium.com/_/stat?event=post.clientViewed&amp;referrerSource=full_rss&amp;postId=168dd6444d52" width="1" /><hr /><p><a href="https://medium.com/neo4j/building-stateful-ai-integrating-aura-agent-lifecycle-with-mcp-and-persistent-memory-168dd6444d52" rel="noopener nofollow" target="_blank">Building Stateful AI: Integrating Aura Agent Lifecycle with MCP and Persistent Memory</a> was originally published in <a href="https://medium.com/neo4j" rel="noopener nofollow" target="_blank">Neo4j Developer Blog</a> on Medium, where people are continuing the conversation by highlighting and responding to this story.</p>
